1. End-to-End System Architecture

The navigation subsystem connects the custom terrain perception pipeline with the standard ROS 2 Navigation 2 (Nav2) controller stack. The verified end-to-end data pipeline is structured as follows:

1. Perception
/terrain/obstacle_features
Terrain detection node publishes detected 3D oriented bounding boxes with centroids and extents.
2. Costmap Bridge
/costmap_bridge_node
Synthesizes dense 3D pointcloud envelopes (Δ = 0.05 m) on topic /bridge/pointcloud.
3. Nav2 Costmaps
global_costmap & local_costmap
Raytrace, mark lethal cells, and generate smooth inflation cost fields ($r = 0.75\text{ m}$).
4. Safety Guard
/collision_monitor
Monitors dynamic footprint approach (1.5s horizon) and clamps cmd_vel to zero upon hazard.

2. Issue 1: 3D Pointcloud Dense Lattice Generation

Source File: PathPlanning/erc_path_planner/src/costmap_bridge_node.cpp

Root Cause

Previously, the bridge node converted each 3D obstacle into a single centroid point or an unpopulated bounding box. This caused costmaps to mark only a single 2D grid cell, allowing Nav2 planners to plan trajectories straight through the physical body of the obstacle. Furthermore, uninitialized header timestamps caused raytracing synchronization errors in TF2.

Before (Single Point Flaw)

// Centroid-only projection
geometry_msgs::msg::Point32 pt;
pt.x = obs.centroid.x;
pt.y = obs.centroid.y;
pt.z = obs.centroid.z;
// Result: 1 single point per obstacle!
// Rayclearing destroys the cell immediately.

After (3D Dense Lattice Sampling)

const float step = 0.05f; // 5 cm resolution
for (float x = obs.min_point.x; x <= obs.max_point.x; x += step) {
  for (float y = obs.min_point.y; y <= obs.max_point.y; y += step) {
    for (float z = obs.min_point.z; z <= obs.max_point.z; z += step) {
      // Dense volumetric envelope
      // 1m x 1m x 0.5m box = 4,851 points!
    }
  }
}

Key Technical Improvements

  • Volumetric Envelope Discretization: Iterates across $(x, y, z)$ from min_point to max_point with step size $\Delta = 0.05\text{ m}$.
  • Automatic Timestamp Fallback: Added if (pointcloud.header.stamp.sec == 0) pointcloud.header.stamp = this->now(); to prevent ROS 2 time synchronization discards.
  • Verification Metric: For a test bounding box of dimensions $1.0\text{ m} \times 1.0\text{ m} \times 0.5\text{ m}$, the bridge generated exactly 4,851 synthetic point measurements, fully covering the obstacle surface and interior.

4. Issue 3: Costmap Inflation & Physical Footprint Modeling

Source File: PathPlanning/erc_path_planner/config/nav2_params.yaml

Rover Geometric Footprint

The rover's geometric dimensions are configured as a 4-point polygon representing a physical bounding box of $1.0\text{ m}$ (length) $\times 0.8\text{ m}$ (width), with an extra safety padding: 

footprint: "[[0.50, 0.40], [0.50, -0.40], [-0.50, -0.40], [-0.50, 0.40]]"
footprint_padding: 0.05

Global Costmap Obstacle & Inflation Layers

The global_costmap was updated to incorporate obstacle_layer fed directly by the perception bridge, paired with a finely tuned inflation_layer:

Parameter Value Engineering Rationale
obstacle_layer.observation_sources pointcloud_source Consumes 3D cloud from /bridge/pointcloud
obstacle_max_range 8.0 m Detects obstacles early for long-range global path generation
raytrace_max_range 10.0 m Clears transient false positives beyond obstacle distance
inflation_radius 0.75 m Safe margin beyond lethal radius ($r_{lethal} \approx 0.50\text{ m}$)
cost_scaling_factor 3.0 Provides smooth gradient decay without trapping the local planner

5. Issue 4: Collision Monitor & Velocity Protocol Alignment

Source Files: PathPlanning/erc_path_planner/config/nav2_params.yaml, testing/PathPlanner/scripts/mock_base.py

1. Nav2 Jazzy Collision Monitor Lifecycle Fix

In ROS 2 Jazzy, configuring static polygons with action_type: "stop" without supplying explicit polygon vertex strings triggers an unhandled parameter exception, causing the lifecycle node to stall in unconfigured [1].

Solution: Configured FootprintApproach dynamically subscribed to /local_costmap/published_footprint with a $1.5\text{ s}$ time-to-collision threshold: 

collision_monitor:
  ros__parameters:
    use_sim_time: True
    base_frame_id: "base_link"
    odom_frame_id: "odom"
    cmd_vel_in_topic: "cmd_vel_smoothed"
    cmd_vel_out_topic: "cmd_vel"
    enable_stamped_cmd_vel: false
    polygons: ["FootprintApproach"]
    FootprintApproach:
      type: "polygon"
      action_type: "approach"
      footprint_topic: "/local_costmap/published_footprint"
      time_before_collision: 1.5
      simulation_time_step: 0.1
      min_points: 2
      visualize: true
    observation_sources: ["pointcloud_source"]
    pointcloud_source:
      type: "pointcloud"
      topic: "/bridge/pointcloud"
      min_height: 0.15
      max_height: 2.0

2. Twist vs TwistStamped Standardization

To prevent message type incompatibilities with rover motor firmware, all velocity topics were unified under the standard un-stamped format:

  • Set enable_stamped_cmd_vel: false across velocity_smoother, controller_server, and collision_monitor.
  • Aligned mock_base.py to subscribe to geometry_msgs/msg/Twist.
