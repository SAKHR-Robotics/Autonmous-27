Control Module (Hardware Interface)

The Control Module is where software mathematically translates into physical electrical voltage. A DC motor has no idea what "0.5 meters per second" means. It only understands PWM current or RPM.

How it works conceptually

  • The controller receives a cmd_vel twist message requesting linear and angular speed.
  • Using the rover's physical dimensions (wheel radius, wheel track width separation), it applies inverse kinematics.
  • If the rover wants to turn right at 0.5 rad/s, it calculates that the left wheels must spin at 120 RPM and the right wheels at 80 RPM.
  • It sends these hardware-specific commands down a UART or CAN-bus line to the physical microcontrollers (e.g., STM32) attached to the motor drivers.

Core ROS 2 Nodes

Usually implemented using the ros2_control framework with a diff_drive_controller or custom skid-steer controller, wrapped around a custom Hardware Interface C++ plugin.

Input & Output Flow

Inputs:

  • /cmd_vel: The velocity requests from the Local Planner.
  • Hardware Encoder Feedback: Raw encoder ticks coming back from the motors via UART/CAN.

Outputs:

  • Hardware Actuation: Electrical signals to the motor drivers.
  • /wheel/odom_raw: The calculated raw wheel odometry, which is fed all the way back up to Saif SLAM for EKF fusion.
