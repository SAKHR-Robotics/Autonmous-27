1. Core Role & System Scope

The Perception Module acts as the environmental recognition engine of the autonomous rover. Its primary responsibility is to transform raw sensor feeds (3D Point Clouds and 2D Camera Frames) into structured geometric telemetry and costmaps so the navigation stack can steer safely around rocks, craters, and steep slopes.

Core Tasks Executed by Perception:

  • Terrain Analysis & Ground Removal: Distinguishes flat driving surfaces from dangerous obstacles using height segmentation algorithms (Patchwork++ / RANSAC).
  • 3D Obstacle Clustering: Filters raw point cloud data using Voxel Downsampling and groups remaining obstacle points into physical 3D bounding boxes using DBSCAN clustering.
  • Costmap Generation: Produces a unified 2D inflated obstacle costmap (/terrain/costmap) ready for direct consumption by Nav2 local and global path planners.
  • Target Recognition (ArUco Vision): Detects mission objective markers in the RGB stream, calculates their ID and exact 3D distance/pose ($X, Y, Z$, Roll, Pitch, Yaw) via OpenCV Perspective-n-Point (PnP) math, and passes anchor updates to SLAM and the State Machine.

1.5. Division of Labor: Perception vs Saif SLAM

To avoid duplicated work and save Jetson Orin Nano compute resources, the tasks between Perception and SLAM are strictly partitioned according to the Saif SLAM Reference Architecture:

What the Perception Module Does:

  • Processes the raw 3D Point Cloud (/camera/depth/color/points).
  • Filters ground terrain and extracts rock obstacle boundaries.
  • Publishes local costmaps (/terrain/costmap) and feature arrays (/terrain/obstacle_features).
  • Executes ArUco marker corner extraction and calculates 3D marker pose (/perception/aruco_pose).

What is Delegated to Saif SLAM (External):

  • Wheel-Inertial Fusion: Running the Extended Kalman Filter (EKF via robot_localization) to broadcast the high-speed odom → base_link transform at 100 Hz.
  • Visual SLAM & Loop Closure: Running RTAB-Map to track camera movement, construct the global map, and output the map → odom drift-correction transform.
  • Encoder Slip Check: Comparing wheel ticks against IMU accelerations to dynamically adjust fusion noise weights.

2.5. Deep Dive: 3D Point Cloud Processing Pipeline

The processing pipeline in terrain_node.py transforms millions of raw 3D depth camera points per second into clean geometric boundaries through 6 distinct mathematical stages:

Stage 1: ROI Spatial Filtering & Coordinate Transformation

Raw point clouds arrive in the camera optical coordinate frame (camera_depth_optical_frame). The node transforms the cloud into the rover's physical center frame (base_link) using tf2. It then crops points outside the driving Region of Interest (ROI) (e.g., $X \in [0.2, 8.0]\text{m}$, $Y \in [-4.0, 4.0]\text{m}$, $Z \in [-0.5, 1.5]\text{m}$) to eliminate chassis self-reflections and far-field camera noise.

Stage 2: Ground Removal (Patchwork++ / RANSAC)

To identify rocks, the node must first remove the flat dirt terrain. It evaluates concentric radial zones and applies Patchwork++ / RANSAC Plane Segmentation to solve for the ground plane equation ($Ax + By + Cz + D = 0$). All points falling within a threshold height ($\le 0.15\text{m}$) of the ground plane are stripped away and sent to the ground debug topic.

Stage 3: Voxel Grid Downsampling

Processing raw point clouds containing over 300,000 points per frame will overload the Jetson Orin Nano CPU. The node applies a 3D Voxel Grid filter with a leaf size of $5\text{cm} \times 5\text{cm} \times 5\text{cm}$. All points inside each $5\text{cm}$ cube are centroid-averaged into a single point, shrinking total data volume by up to 90% while preserving obstacle shape.

Stage 4: Radius Outlier Removal (ROR)

Airborne dust or sensor noise can produce floating "ghost" points. The ROR filter searches a sphere of radius $r=0.2\text{m}$ around every point. If a point has fewer than 5 neighboring points inside that sphere, it is discarded as sensor noise.

Stage 5: DBSCAN Euclidean Clustering

The remaining obstacle points are grouped using DBSCAN (Density-Based Spatial Clustering of Applications with Noise) with a cluster radius $\epsilon = 0.3\text{m}$. Nearby points are clustered into distinct objects (individual rocks). For each cluster, the node calculates its 3D centroid, bounding box dimensions ($X_{size}, Y_{size}, Z_{size}$), and Euclidean distance to the rover.

Stage 6: Occupancy Grid & Costmap Inflation

The detected clusters are rasterized onto a 2D grid ($200 \times 200$ cells at $5\text{cm}$ resolution). The node inflates obstacle boundaries by the rover's footprint radius ($0.3\text{m}$) plus a safety inflation buffer ($0.6\text{m}$), producing an exponential cost decay gradient (values $0 \dots 100$) so Nav2 path planners keep a safe distance from rocks.

4.5. Component & Codebase Breakdown

Package Location: Autonmous_Ws/Perception/terrain_geometry_improved/terrain_geometry

  • terrain_node.py: Main ROS 2 executable node orchestrating parameters, subscriptions, execution stages, and publishing streams.
  • ground_removal.py: Contains RANSAC and Patchwork++ ground extraction algorithms.
  • voxel_filter.py: Implements 3D spatial voxel grid downsampling.
  • outlier_filter.py: Implements Radius Outlier Removal (ROR).
  • clustering.py: Implements DBSCAN Euclidean clustering and bounding box extraction.
  • occupancy_grid.py & costmap_inflation.py: Converts 3D clusters to 2D occupancy cells and applies exponential cost inflation.
  • tf_transform.py: Manages coordinate frame transformations between camera frames and base_link.
  • terrain_geometry_msgs: Custom interface package defining ObstacleFeature and ObstacleFeatureArray ROS 2 messages.

5. ArUco Marker Vision & 3D PnP Distance Math

ArUco detection operates on 2D color images and uses projective geometry to calculate 3D position without suffering from depth sensor infrared noise or sunlight blinding.

How 3D Distance is Calculated (Perspective-n-Point):

  1. Corner Detection: OpenCV scans the RGB frame (/camera/color/image_raw) to detect the 4 square corners of the ArUco marker in 2D image coordinates ($(u, v)$ pixels).
  2. Marker Decoding: Reads the internal binary matrix code to identify the Marker ID number.
  3. SolvePnP Math: By feeding the known physical marker size (e.g., $20\text{cm}$ square), the 4 pixel corner coordinates, and the camera calibration matrix ($f_x, f_y, c_x, c_y$ from /camera/camera_info), OpenCV solves the Perspective-n-Point (PnP) transformation: $$\begin{bmatrix} u \\ v \\ 1 \end{bmatrix} = \mathbf{K} \begin{bmatrix} \mathbf{R} & \mathbf{t} \end{bmatrix} \begin{bmatrix} X \\ Y \\ Z \\ 1 \end{bmatrix}$$
  4. 3D Pose Output: This outputs the exact 3D translation vector $\mathbf{t} = [X, Y, Z]$ (distance forward, left, and up) and rotation vector $\mathbf{R}$ (angles) relative to the camera optical frame.
  5. Temporal & Distance Gating (Noise Rejection): To prevent transient false positives or high optical jitter from corrupting SLAM coordinates, the node applies gating:
    • Distance Gating: Ignore markers situated beyond 3.5 meters from the camera, as depth calculation errors grow exponentially with distance.
    • Temporal Gating: Only publish the marker pose on /perception/aruco_pose if the same Marker ID is detected continuously across at least 3 consecutive frames.

Integration with Saif SLAM:

The node publishes this data on /perception/aruco_pose. When RTAB-Map in Saif SLAM receives this pose, it matches the marker ID against surveyed arena coordinates and applies a global map correction to eliminate accumulated wheel drift.

6. Synchronization with Saif SLAM & Nav2

To ensure Perception, Saif SLAM, and Nav2 work seamlessly together without latency or coordinate mismatch, enforce the following configuration rules:

  • TF Chain Consistency: Ensure perception's target frame parameter is set to base_link. The ROS 2 TF tree parent-to-child flow runs downwards from the map:
    map → odom → base_link → camera_link → camera_depth_optical_frame
  • QoS Policy Matching: RealSense cameras publish point clouds with Best Effort QoS. The perception subscription must use QoSReliabilityPolicy.BEST_EFFORT to avoid dropped frames. Perception outputs use RELIABLE QoS so Nav2 never misses a costmap update.
  • Depth Camera Driver Outputs: Configure the camera driver (realsense2_camera node) to publish both standard depth/RGB image frames for RTAB-Map SLAM and the 3D Point Cloud topic (/camera/depth/color/points) by setting enable_pointcloud:=true in your launch parameters.
  • Compute Optimization: Set point cloud processing rates to **10–15 Hz** on the Jetson Orin Nano to leave sufficient GPU/CPU headroom for RTAB-Map and Nav2.

# Source workspace and launch terrain geometry node
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 launch terrain_geometry terrain.launch.py

# Terminal 1: Launch Gazebo world and spawn rover
ros2 launch my_robot_description gazebo.launch.py world:=world1.world

ros2 launch terrain_geometry terrain.launch.py

Troubleshooting RViz Mismatch Warnings:

If point clouds or raw images fail to show in RViz, change the Reliability Policy setting inside the RViz display dropdown from Reliable to Best Effort. RealSense drivers publish sensor topics with Best Effort QoS by default.
